07_API_Design: MedScreen Festival & Event SuiteEdiția Specială: Tradiții Argeșene, Ediția XIIIRol: Senior API Architect & Backend Solution Architect (Enterprise Medical Systems)Status Document: Proiectare Completă a Interfețelor de Programare (Fără Cod de Implementare)

1. Scopul API-urilorAcest document definește specificația tehnică oficială a interfețelor de programare a aplicației MedScreen Festival & Event Suite. Scopul este crearea unui contract uniform, sigur și predictibil între stratul de client (PWA / Tablete / Mobile) și serverul backend enterprise, facilitând comunicarea bidirecțională, sincronizarea offline-first și managementul operațional fără ambiguități.

2. Principijile Arhitecturii RESTStatelessness: Fiecare cerere HTTP de la client trebuie să conțină toate informațiile necesare pentru înțelegerea și procesarea sa (prin token JWT).Resurse Orientate pe Noun-uri: Endpoint-urile utilizează substantive la plural pentru resurse (/api/v1/patients, /api/v1/screenings), evitând verbele în URL.Separarea Responsabilităților: Răspunsurile urmează standardul de structură JSON, separând datele efective de metadate și stări.

3. Convenții API și VersionareFormat Schimb Date: JSON pur (application/json).Versionare: Versiunea este inclusă în calea URL-ului pentru a garanta compatibilitatea retroactivă (ex: /api/v1/...).Naming Conventions: Utilizarea formatului snake_case pentru proprietățile din corpul cererilor/răspunsurilor JSON și kebab-case pentru segmentele URL multiple.

4. Autentificare, Autorizare și SecuritateMecanism de Autentificare: Bearer Token bazat pe JSON Web Tokens (JWT) emis la autentificarea cu succes în endpoint-ul de login.Controlul Accesului (RBAC): Fiecare endpoint specifică clar rolurile permise (admin, medic, operator). Lipsa rolului adecvat returnează imediat codul HTTP 403 Forbidden.Securitate în Tranzit: Toate cererile trebuie efectuate exclusiv prin protocolul HTTPS (TLS 1.3).

5. Structura Request-urilor și Response-urilorA. Structura Standard a unui Răspuns de SuccesJSON{  "status": "success",  "code": 200,  "message": "Operațiunea a fost efectuată cu succes.",  "data": {    // Obiectul sau lista returnată  },  "meta": {    "timestamp": "2026-07-30T14:22:53Z",    "version": "1.0.0"  }}B. Structura Standard a unui Răspuns de EroreJSON{  "status": "error",  "code": 400,  "error": {    "code": "INVALID_PARAMETER",    "message": "Parametrul 'systolic_bp' este în afara limitelor fiziologice permise.",    "details": [      {        "field": "systolic_bp",        "issue": "Valoarea trebuie să fie între 50 și 260."      }    ]  },  "meta": {    "timestamp": "2026-07-30T14:22:53Z"  }}

6. Codurile HTTP Utilizate200 OK: Cerere reușită, returnează date.201 Created: Resursă creată cu succes (ex: screening nou, pacient nou).400 Bad Request: Date invalide sau eroare de validare client.401 Unauthorized: Token JWT lipsă sau expirat.403 Forbidden: Utilizatorul nu are rolul necesar pentru acțiune.404 Not Found: Resursa căutată nu există.409 Conflict: Conflict la sincronizarea offline (duplicat UUID).500 Internal Server Error: Eroare neașteptată pe server.

7. Rate Limiting, Logging și AuditRate Limiting: Maximum 100 de cereri pe minut per adresă IP / utilizator pentru a preveni atacurile de tip brute-force sau DoS.Logging & Audit: Orice cerere modificatoare (POST, PUT, DELETE) generează automat o înregistrare în tabela de audit (audit_logs) conținând utilizatorul, IP-ul, acțiunea și timestamp-ul.

8. Paginație, Filtrare, Sortare și CăutarePaginare: Realizată prin query parametri: ?page=1&limit=20.Filtrare: ?triage_level=red&city=Pitesti.Sortare: ?sort_by=created_at&order=desc.Căutare: ?search=Popescu sau ?phone=0722.

9. Specificația Detaliată a Endpoint-urilor API9.

1. API pentru AutentificarePOST /api/v1/auth/loginScop: Autentificarea utilizatorului și emiterea tokenului JWT.Parametri: Niciunul în URL.Date primite (Body): username (string), password (string).Date returnate: Token JWT, rol utilizator, nume complet.Validări: Câmpuri obligatorii, verificarea hash-ului parolei.Autentificare: Publică.Roluri permise: Oricine (Public).Coduri de răspuns: 200 OK, 400 Bad Request, 401 Unauthorized.Mesaje de eroare: Nume de utilizator sau parolă incorecte.Dependențe: Modulul de securitate și criptare parole (Argon2id).Observații: Tokenul are valabilitate limitată (ex: 8 ore pentru tura de festival).POST /api/v1/auth/logoutScop: Invalidează sesiunea curentă / tokenul clientului.Autentificare: Necesară (Bearer Token).Roluri permise: Toate rolurile active.Coduri de răspuns: 200 OK, 401 Unauthorized.9.

2. API Utilizatori și RoluriGET /api/v1/usersScop: Listarea tuturor utilizatorilor sistemului.Autentificare: Necesară.Roluri permise: admin.Coduri de răspuns: 200 OK, 403 Forbidden.POST /api/v1/usersScop: Crearea unui cont nou de operator sau medic.Date primite: username, full_name, role, password.Roluri permise: admin.Coduri de răspuns: 201 Created, 400 Bad Request.9.

3. API PaciențiGET /api/v1/patientsScop: Căutarea sau listarea pacienților după numër de telefon sau nume.Parametri: ?phone=0722... sau ?search=....Autentificare: Necesară.Roluri permise: admin, medic, operator.Coduri de răspuns: 200 OK.POST /api/v1/patientsScop: Înregistrarea unui pacient nou.Date primite: first_name, last_name, phone, age, gender, city.Autentificare: Necesară.Roluri permise: admin, medic, operator.Coduri de răspuns: 201 Created, 400 Bad Request.9.

4. API Screening și Motor ClinicPOST /api/v1/screeningsScop: Înregistrarea unui screening complet, procesarea prin motorul clinic, generarea triajului și a codului de reducere.Date primite: id (UUID client), patient_id, systolic_bp, diastolic_bp, pulse, weight, height, has_diabetes, diabetes_type, takes_htn_meds, smoker, family_history_cvd, gdpr_consent, patient_signature (Base64).Date returnate: Rezultatul calculat al triajului (triage_level), recomandările automate, codul de reducere emis (discount_code).Validări: Verificarea plauzibilității datelor fiziologice, existența acordului GDPR.Autentificare: Necesară.Roluri permise: admin, medic, operator.Coduri de răspuns: 201 Created, 400 Bad Request, 409 Conflict (dacă UUID-ul există deja).Dependențe: Motorul de Suport Decizional Clinic (CDSS).GET /api/v1/screenings/{id}/historyScop: Obținerea istoricului screeningurilor pentru un anumit pacient.Autentificare: Necesară.Roluri permise: admin, medic, operator.Coduri de răspuns: 200 OK, 404 Not Found.9.

5. API Sincronizare Offline (Offline Sync & Conflict Resolution)POST /api/v1/sync/batchScop: Sincronizarea în masă a înregistrărilor salvate offline pe dispozitiv în timpul funcționării fără internet.Date primite: O listă de obiecte JSON conținând screeninguri, pacienți și jurnale locale, fiecare având un UUID unic generat de client și timestamp.Date returnate: Raport de sincronizare (înregistrări procesate cu succes, înregistrări cu conflicte rezolvate).Autentificare: Necesară.Roluri permise: admin, medic, operator.Coduri de răspuns: 200 OK, 400 Bad Request.Observații de implementare: Implementează politica Last-Write-Wins / Client-Timestamp Precedence și scrie automat în audit_logs în caz de discrepanțe.9.

6. API Raport PDF și Semnătură GDPRGET /api/v1/screenings/{id}/pdfScop: Descărcarea sau generarea fișierului PDF oficial pentru un screening.Autentificare: Necesară.Roluri permise: admin, medic, operator.Coduri de răspuns: 200 OK (returnează fișier binar application/pdf), 404 Not Found.9.

7. API Export ExcelGET /api/v1/exports/excelScop: Generarea și descărcarea fișierului tabelar .xlsx centralizat pentru statistici și campanii.Parametri: ?campaign_id=...&start_date=...&end_date=...Autentificare: Necesară.Roluri permise: admin, medic.Coduri de răspuns: 200 OK (returnează fișier application/vnd.openxmlformats-officedocument.spreadsheetml.sheet).9.

8. API Reguli Clinice (Configurabile)GET /api/v1/clinical-rulesScop: Preluarea setului activ de reguli clinice și praguri pentru evaluare locală/centrală.Roluri permise: admin, medic, operator.Coduri de răspuns: 200 OK.PUT /api/v1/clinical-rules/{id}Scop: Actualizarea pragurilor sau a condițiilor unei reguli clinice (fără cod).Date primite: parameter_conditions (JSON), resulting_triage, resulting_recommendations.Roluri permise: admin.Coduri de răspuns: 200 OK, 400 Bad Request.9.

9. API Jurnal Audit și Sănătate Sistem (Health Check)GET /api/v1/audit-logsScop: Vizualizarea jurnalului de securitate și audit.Roluri permise: admin.Coduri de răspuns: 200 OK.GET /api/v1/healthScop: Verificarea stării de funcționare a serverului și a bazei de date centrale.Autentificare: Publică (pentru load balancer / probe).Roluri permise: Toți.Coduri de răspuns: 200 OK, 503 Service Unavailable.

11. Exemple de Fluxuri APIFluxul 1: Efectuarea unui Screening și Sincronizarea Local-CloudClientul trimite POST /api/v1/screenings cu datele măsurătorilor.Serverul validează datele, rulează motorul clinic, generează codul de reducere și salvează în PostgreSQL (201 Created).Dacă rețeaua este căzută, clientul salvează local în IndexedDB și trimite ulterior cererea prin POST /api/v1/sync/batch la revenirea conexiunii.Fluxul 2: Actualizarea Pragurilor Clinice de către AdministratorAdministratorul accesează panoul și trimite PUT /api/v1/clinical-rules/{id} cu noile praguri JSONB.Serverul validează rolul de admin, actualizează tabela clinical_rules_config și înregistrează acțiunea în audit_logs.

12. Recomandări pentru Implementare și ConcluziiToate răspunsurile de eroare trebuie să urmeze strict structura definită la capitolul 5 pentru a permite gestionarea uniformă în interfața grafică (PWA).Utilizarea tranzacțiilor la nivel de bază de date pentru endpoint-ul de screening garantează că pacientul, măsurătorile și recomandările sunt salvate atomic, prevenind stările parțiale corupte.
